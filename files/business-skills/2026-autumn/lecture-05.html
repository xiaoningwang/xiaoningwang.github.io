一、三笔费用能通过预检吗

一场学生活动的预算是300元。三笔费用分别申请120元、80元和100元，前两笔能在凭证上找到相同金额，第三笔尚未提交凭证。经办人需要同时看到两个结论：申请总额恰好用完预算，其中200元已匹配凭证，100元待补。若系统只显示一个绿色的“通过”，就丢掉了经办人下一步要做的事。

费用编号 申请／元 凭证／元 申请减凭证／元 逐笔结果
F01 120 120 0 已匹配
F02 80 80 0 已匹配
F03 100 缺 待核 待补凭证

本讲用这份清单比较扣子编程、Dify 与阿里云百炼。学完后，应能为自己的商业项目选择开发方式，写出模型、程序与经办人的分工，并用能够复现的输入检验结果。

二、模型能处理哪些输入，结果怎样验收

模型可以读取凭证图片、抽取字段、提出工具调用并起草说明。开发平台把文件、模型、计算节点、权限和运行记录连成流程。AI 编程助手则可以修改复核页的代码、运行程序并检查改动。出现“合计金额算错”时，先看送入计算节点的数值，便能区分是读错了凭证，还是算错了合计。

2026年11月的模型与接口

官方记录 与开发有关的变化 可以怎样检验
DeepSeek，11月13日 开放文件输入、联网搜索、链接阅读等应用接口 读取活动制度，核对模型返回的条款位置。 [1]
百炼，11月16日、19日 上架 Qwen4-Max 正式版和北京地域 Kimi-K3.1-Pro-Prime。前者支持图像、工具调用与结构化输出，后者面向响应速度敏感的任务 固定相同图片和字段，比较金额正确性与完整任务耗时。 [2] [3]
Anthropic，11月9日 Claude Fable 5.2 更新编码、推理与视觉能力 给出导致金额重复累加的输入，检查修复后是否仍能通过原例。 [5]
OpenAI，11月17日 GPT-6.2 Astra 与 Sol 接受文本和图片。两者面向不同的推理、速度与成本需求 在相同设置下比较凭证字段、等待时间和调用费用。 [4]
Google DeepMind，11月18日 Gemini 4 Neon 面向软件工程与知识工作，可通过 Gemini API 接入 让模型修改录入和导出两个环节，再比较导出表与页面合计。 [6]

验收基准。 凭证写“合计80.00元”，预期抽出80.00和人民币元。若申请80元、凭证79元，预期输出差额1元。若仅有申请单，凭证金额应留空。比较模型时固定输入、提示、工具与输出字段，记录实际模型标识、日期和推理设置。

成本算例。 自11月18日12时起，DeepSeek 模型内部触发的服务端搜索与网页抓取不另收工具调用费，返回的内容进入上下文后计入模型用量。程序直接调用独立 Search 或 Fetch 接口时，则按每千次成功请求5元计费。两次搜索加一次抓取均成功，独立接口费为0.015元，随后交给模型总结的用量另计。 [1]

三、三个平台如何处理同一条异常

把 F02 的凭证由80元改为79元，申请仍是80元。无需模型判断“差一元是否算错”，程序可以直接算出差额。平台的选择取决于谁来接收结果、能否追溯输入，以及经办人如何更正。

扣子编程：在画布上查看输入与输出

扣子提供使用智能体与技能的入口，扣子编程提供开发智能体、工作流及应用的工作台。扣子侧自2026年9月8日起用 Agent 中的编程开发和部署运维插件承接新项目的开发、部署。 [7] [8]

在开始节点传入三笔费用和预算，在计算节点输出逐笔状态、差额与批次合计。条件分支把 F03 送入补件清单，把改成79元的 F02 送交人工复核。在画布点击这两个节点，看异常编号是否完整传到摘要。用 API 运行已发布的工作流时，可通过返回的 debug_url 查看节点输入与输出。套餐资源和发布入口依项目类型而定。 [10] [11]

Dify：让经办人决定异常如何处理

Workflow 适合处理一批明细，Chatflow 可承接带上下文的对话。New Agent 可以独立使用，也可在工作流里复用。配置模式用于选择模型、提示、文件、工具与技能，Build mode 支持通过对话拟定配置，再预览草稿。 [14] [15]

当 F02 出现1元差额时，人工介入节点暂停流程，表单同时显示编号、申请、凭证和差额。经办人可选择“退回补件”或“确认更正”。更正后保存原值和新值，并重新计算。超时分支保留待办记录。调试时查看节点追踪，编辑器中的 Workflow 或 Chatflow 预览、测试运行与已发布应用的运行日志分别查看。 [17]

阿里云百炼：把条款检索与金额计算连起来

Flow Agent 支持工作流和智能体应用。固定的核验顺序可用脚本节点计算，再用条件节点分支。若经办人询问本次活动为何限额300元，Agent 2.0 可使用知识库检索工具；配置“必定调用”时，会在首次推理前检索。将找出的条款、规则版本传给后续节点。台账与制度版本不同，先把冲突列出来，交经办人确认。 [12] [16]

选平台时，可以直接做三个小试验：在扣子画布找到差额的输入，在 Dify 表单处理一次超时，在百炼查到上限所依据的条款。计划自部署的项目还要核对许可。Coze Studio 采用 Apache 2.0，Dify 在 Apache 2.0 基础上设有附加条件。自部署时，外部模型或插件仍按实际连接接收调用数据。 [13] [18]

四、工具、技能与任务状态

工具提供可执行能力。费用核验工具接收编号和金额，返回差额、状态与错误信息。API 定义服务怎样接收调用，MCP 让应用以约定的接口接入工具和上下文。一个平台可以调用别人的 MCP 工具，也可以把自己的应用作为 MCP 服务提供给其他应用。两种连接分别配置权限与参数。 [19] [20]

技能（Skill）保存可重复使用的方法。以扣子为例，可以在 SKILL.md 中说明何时核对凭证、怎样标记缺失、以何种格式交付；字段字典、脚本和模板随技能组织。本次活动的300元上限从活动记录或适用制度传入，下次活动可以使用另一份已确认预算。 [9] [19]

任务状态记录这一次的事实。F03 的凭证在补交之前保持“待补凭证”。收到新文件、核对到100元、保存更正后，才能更新状态。下一次对话仍应通过费用编号找回记录。规则版本、用户偏好和当前核验结果各有不同的更新条件。

五、给编程助手一项可验收的修改

可视化工作流适合按固定步骤读取、计算和分流。项目还需要可编辑表格、自定义导出或特殊计算时，可以用 AI 编程实现界面或计算模块。对话式工具可用自然语言搭原型，Codex、Claude Code 等项目工具还可读取文件、修改实现并运行测试。 [8] [21] [22]

在费用复核页加一列凭证金额，允许暂时留空。申请总额包括所有有效申请，已匹配金额只累计凭证与申请一致的行。编辑一笔已有费用后，刷新页面仍能看到同一条记录。

给助手提供原始三行作为输入。在 F03 的原行补入100元后，记录数应仍为三行，申请总额仍为300元，已匹配金额由200元变为300元。如果申请总额变成400元，先检查“保存修改”是否调用了新增记录的逻辑。修复后再次运行补件和重复导入两个用例，并核对导出清单。

作为延伸阅读，可在 AI-Trader 开源仓库对照技能说明与 OpenAPI 接口定义，找出一个查询接口的输入、返回、凭据与失败状态。 [23]

六、课堂练习：核对三笔活动费用

你是活动经办人。 预算300元。你要让下一位经办人一眼看出已申请多少、多少有凭证、哪一笔要补件或复核。每人选一种课堂讲过的工作流平台或 AI 编程工具，完成以下练习。

第一步，录入原始清单。 将下列三行导入原型，金额单位为元。F03 的凭证金额保留为空。先自行写出申请总额、已匹配金额和待补编号，再运行原型，对照三个结果。

费用编号,申请金额,凭证金额
F01,120,120
F02,80,80
F03,100,

第二步，逐项测试。 每次恢复上面的三行，再改变下表的一项。有效申请计入预算，申请与凭证金额一致才计入已匹配金额。完全相同的行只计一次并保留重复记录。同编号的金额互相冲突时，交经办人核对后再确定总额。

单独改变的输入 预期输出
F03 补入100元凭证 已匹配300元，总申请仍为300元
再导入完全相同的 F02 提示重复，总申请仍为300元
F02 凭证改为79元 F02 差额1元，转人工复核。F03 仍在补件清单中
F03 申请改为100.01元 超预算0.01元，F03 仍待补凭证
让金额核验步骤返回一次“超时”（可在测试分支直接返回这个状态） 保存输入，标记核验未完成，等待重新核验

第三步，留下可复查的记录。 五个用例各占一行，填写“改了什么｜预期结果｜实际结果｜通过或待修订”。实际结果抄录系统返回的金额、编号或状态。有偏差时，保留原输出，写明在哪个步骤修改以及复测结果。原始清单应显示申请300元、已匹配200元、F03待补100元。给 F03 补凭证后，系统应仍显示三笔申请。

读懂复核指标。 另有12笔申请，人工确认4笔需要复核，系统标出5笔，其中3笔确需复核。先写下误报、漏报各几笔，分别说出谁会受影响，再核对算式。查准率为 3/5=60%3/5=60\%，召回率为 3/4=75%3/4=75\%。误报2笔增加了经办人的复核量，漏报1笔可能让有问题的费用继续流转。 [24]

七、个人期中项目汇报

本讲每人提交一份期中项目说明。 课堂的五行测试记录用来练习验收。汇报时沿用自己的商业项目，选可视化工作流或 AI 编程，把正常与异常运行的证据放进同一份说明。可以直接使用课堂记录的格式。

  1. 说明目标使用者、现有做法、一个待解决的问题，以及为什么选择该平台。
  2. 并列展示一次正常运行和一次异常运行的输入、预期与实际结果，附关键节点记录或界面截图，标出谁处理异常。
  3. 用同一输入比较原办法与原型的耗时或错误，说明样本数，并写出一项本人完成的核验或修改。

交前自查。 读者应能用你给出的输入重现两次运行，指出异常交给谁处理，并从原始记录看懂耗时或错误数的比较。
